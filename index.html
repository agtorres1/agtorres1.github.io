Enviar S.A. — Sales Dashboard in Power BI

A distribution company needed a single place to monitor sales, margins, shipping costs and its provincial managers.

Three-page Power BI report built on a star-schema data warehouse: KPIs compared with the previous year, a map of Argentina with profit by province, product and customer rankings, and logistics costs.

Full details for Enviar S.A.
Problem
Enviar S.A. sells technology, furniture and office supplies across Argentina. Management needed to track monthly and year-to-date sales, best-selling products, shipping methods, top customers by segment, monthly margin per provincial manager and the products with the highest shipping cost.
Solution
A Power BI model over the company's star-schema data warehouse (sales fact table plus product, customer, segment, province, shipping, priority, packaging and distribution-center dimensions) with an added date table. DAX measures cover year-over-year comparison, year-to-date totals, top-10 rankings and conditional colors. The report is organized by business question rather than by assignment item, with a custom background design, side navigation, synchronized filters and a findings panel.

SQL Server Data Migration & BI

A real-estate agency ran its whole operation from one denormalized table of about 90 columns.

Normalized transactional model, full data migration with stored procedures, and a star-schema BI model with 9 indicator views.

  1. Transactional model (implemented)
  2. Data migration (implemented)
  3. BI model (implemented)
  4. Verification (implemented)
  • SQL Server 2019
  • T-SQL
  • Stored procedures
Full details for SQL Server Data Migration & BI
Problem
A real-estate agency kept its whole operation — properties, owners, listings, agents, branches, sales, rentals, tenants and payments — in a single denormalized table of about 90 columns, with data mixed and repeated in every row.
Solution
A normalized transactional model in SQL Server: a T-SQL stored procedure creates its 29 tables with primary and foreign keys, documented in a full entity-relationship diagram. Design choices include a shared Person entity with role tables, catalogs for every typed value, a Province → City → Neighborhood hierarchy and a many-to-many property-features relation. Stored procedures migrate the data in dependency order without modifying the source; a star-schema BI model (9 dimensions, including time, location, branch, age range and surface range) feeds 9 indicator views such as rent delinquency, listing-to-deal conversion, price per m² and commissions per branch; and a verification script compares row counts between source and target.
Technologies
SQL Server 2019, T-SQL (DDL, DML, stored procedures, views), SQL Server Management Studio
Status
Completed — academic project, Data Management course, UTN FRBA. The source database provided by the course is not included in the repository.

TSU Academic Tracking

A tutoring program tracked students across 15+ inconsistent Excel spreadsheets.

Synthetic data. All data in this project is synthetic. Results illustrate the method and do not describe the real program.

Python pipeline that consolidates every sheet into one relational dataset, with incremental loads through Google Forms and a Looker Studio dashboard.

  • Python
  • pandas
  • Apps Script
  • Looker Studio
Full details for TSU Academic Tracking

All data in this project is synthetic. It is generated to mimic the shape and messiness of the real spreadsheets without copying any rows. Results illustrate the method and do not describe the real program.

Problem
A university tutoring program tracked its students across 15+ inconsistent Excel spreadsheets, with different headers, free-text codes, color-coded cells and students recorded with differently formatted IDs. Leadership needed to know how much academic activity students recover after the program and which profiles engage, without cross-referencing spreadsheets by hand.
Solution
A Python pipeline that consolidates all spreadsheets into a single relational dataset, decoding each cell (text and color) and resolving identities by national ID, then email, then name — never merging two different IDs — with a manual review queue. Incremental loading runs through Google Forms and Apps Script, imports from the academic office are idempotent, and a Looker Studio dashboard covers the funnel, post-program activity and student profiles. The analysis is deliberately descriptive (rates with Wilson confidence intervals) rather than predictive.
Technologies
Python (pandas, openpyxl, matplotlib), Jupyter, Google Forms, Google Sheets and Apps Script, Looker Studio
Status
Completed.

Estimate which bank customers are most likely to purchase a new product bundle.

Supervised classification model built with the KDD methodology and designed for end-to-end productionization on Azure Machine Learning.

  • Python

Full details for Cross-sell Model — Azure MLOps
Problem
A bank needs to estimate which customers are most likely to purchase a new product bundle, in order to improve conversion in marketing campaigns and contact queues.
Solution
A supervised classification model built with the KDD methodology: an analytic base table at customer level with aggregate features over 3- and 6-month windows, a one-month lead window to avoid data leakage, and comparison of Logistic Regression, Decision Tree, Random Forest and LightGBM evaluated with ROC-AUC, KS and lift by decile. The project is designed for end-to-end productionization on Azure Machine Learning: versioned data assets, SDK v2 pipelines reusing the same code as the notebooks, a quality gate before model registration, managed endpoints for scoring and drift monitoring.
Technologies
Python, scikit-learn and LightGBM, Azure Machine Learning (SDK v2), MLflow

StockifAI2 — Inventory Management

In automotive workshops, too many spare parts tie up money and become obsolete, while too few leave cars waiting for a part.

A complete web product that centralizes the stock of one or several workshops, predicts weekly demand per spare part for the next 4 weeks and raises automatic alerts for imminent stock-outs, low stock and overstock.

  • MySQL 8

Full details for StockifAI2
Problem
In automotive workshops and dealerships, too many spare parts tie up money and become obsolete, while too few leave cars waiting for a part.
Solution

A complete web product that centralizes the stock of one or several workshops, predicts weekly demand per spare part for the next 4 weeks and raises automatic alerts for imminent stock-outs, low stock and overstock.

Features include an inventory dashboard with KPIs and Excel reports, rotation classification for each part, a map to locate which workshop in the group has a part in stock, a parts catalog, bulk stock import from Excel, and workshops, groups and users with roles.

The ML pipeline segments parts into frequent and intermittent sellers, builds lag, rolling-window, calendar (including Argentine holidays) and macroeconomic features, trains one LightGBM model per segment with time-ordered validation and rolling forecasts, and runs automatically every week or on demand through the API.

Technologies
  • Frontend: Angular 18, Bootstrap 5, Chart.js, Leaflet
  • Backend: Django 5, Django REST Framework, django-crontab
  • Machine learning: LightGBM, scikit-learn, pandas, NumPy
  • Database: MySQL 8
  • Authentication: Auth0 (JWT)
  • Infrastructure: AWS, Nginx, Gunicorn
