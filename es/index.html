Business Intelligence

Finalizado

Enviar S.A. — Tablero de ventas en Power BI

Una empresa de distribución necesitaba un solo lugar para seguir ventas, márgenes, costos de envío y el desempeño de sus gerentes provinciales.

Reporte de Power BI de tres páginas sobre un data warehouse en estrella: KPIs contra el año anterior, un mapa de Argentina con el lucro por provincia, rankings de productos y clientes, y costos logísticos.

  • Mobiliario factura $5,2 M pero deja solo 2,3 % de margen, contra 14,8 % de Tecnología.
  • El 51 % de las líneas de venta da pérdida; con descuentos de más del 5 %, el margen cae de 11,9 % a 7,8 %.
  • Las ventas crecieron 7,6 % entre 2022 y 2024, con un margen estable de 10–11 %.
  • Power BI
  • DAX
  • Power Query
  • Modelo estrella
  • Storytelling con datos
Ver detalle de Enviar S.A.
Problema
Enviar S.A. vende tecnología, mobiliario y material de escritorio en todo el país. La gerencia necesitaba seguir las ventas mensuales y acumuladas del año, los productos más vendidos, las formas de envío, los principales clientes por segmento, el margen mensual de cada gerente provincial y los productos con mayor costo de envío.
Solución
Un modelo de Power BI sobre el data warehouse en estrella de la empresa (tabla de hechos de ventas y dimensiones de producto, cliente, segmento, provincia, envío, prioridad, embalaje y centro de distribución), con una tabla de calendario agregada. Las medidas DAX cubren comparación interanual, acumulado del año, rankings top 10 y colores condicionales. El reporte está organizado por pregunta de negocio y no por consigna, con un fondo diseñado a medida, navegación lateral, filtros sincronizados y un panel de hallazgos.
Tecnologías
Power BI Desktop, DAX (inteligencia de tiempo, RANKX), Power Query, modelado dimensional, formato de proyecto de Power BI (PBIP)
Estado
Finalizado — electiva Inteligencia de Negocios, UTN FRBA (2025), rediseñado en 2026.

Migración de datos y BI en SQL Server

Una inmobiliaria manejaba toda su operación en una sola tabla desnormalizada de unas 90 columnas.

Modelo transaccional normalizado, migración completa de los datos con stored procedures y un modelo de BI en estrella con 9 vistas de indicadores.

  1. Modelo transaccional (hecho)
  2. Migración (hecho)
  3. Modelo de BI (hecho)
  4. Verificación (hecho)
  • SQL Server 2019
  • T-SQL
  • Stored procedures
Ver detalle de SQL Server Data Migration & BI
Problema
Una inmobiliaria tenía toda su operación (inmuebles, propietarios, anuncios, agentes, sucursales, ventas, alquileres, inquilinos y pagos) en una única tabla desnormalizada de unas 90 columnas, con datos mezclados y repetidos en cada fila.
Solución
Un modelo transaccional normalizado en SQL Server: un stored procedure en T-SQL crea sus 29 tablas con claves primarias y foráneas, documentadas en un DER completo. Entre las decisiones de diseño: una entidad Persona común con tablas de roles, catálogos para todos los valores tipificados, una jerarquía Provincia → Localidad → Barrio y una relación N:M entre inmuebles y características. Los stored procedures migran los datos en orden de dependencias sin modificar el origen; un modelo de BI en estrella (9 dimensiones, entre ellas tiempo, ubicación, sucursal, rango etario y rango de superficie) alimenta 9 vistas de indicadores como morosidad en alquileres, conversión de anuncios en operaciones, precio del m² y comisiones por sucursal; y un script de verificación compara cantidades entre origen y destino.
Tecnologías
SQL Server 2019, T-SQL (DDL, DML, stored procedures, vistas), SQL Server Management Studio
Estado
Finalizado — proyecto académico de Gestión de Datos, UTN FRBA. La base de origen provista por la cátedra no está incluida en el repositorio.

Seguimiento académico TSU

Un programa de tutorías seguía a sus estudiantes en más de 15 planillas de Excel inconsistentes.

Datos sintéticos. Todos los datos del proyecto son sintéticos. Los resultados ilustran el método y no describen al programa real.

Pipeline en Python que consolida todas las planillas en un único dataset relacional, con cargas incrementales desde Google Forms y un tablero en Looker Studio.

  • Python
  • pandas
  • Apps Script
  • Looker Studio
Ver detalle de TSU Academic Tracking

Todos los datos del proyecto son sintéticos: imitan la forma y el desorden de las planillas reales sin copiar ninguna fila. Los resultados ilustran el método y no describen al programa real.

Problema
Un programa universitario de tutorías seguía a sus estudiantes en más de 15 planillas de Excel inconsistentes: encabezados distintos, códigos en texto libre, celdas marcadas con colores y documentos cargados con formatos diferentes. La coordinación necesitaba saber cuánta actividad académica recuperan los estudiantes después del programa y qué perfiles se involucran, sin cruzar planillas a mano.
Solución
Un pipeline en Python que consolida todas las planillas en un único dataset relacional: decodifica cada celda (texto y color) y resuelve identidades por DNI, luego email y luego nombre, sin unir nunca dos documentos distintos, con una cola de revisión manual. La carga incremental funciona con Google Forms y Apps Script, las importaciones de alumnos son idempotentes y un tablero en Looker Studio muestra el embudo, la actividad posterior al programa y los perfiles de estudiantes. El análisis es descriptivo a propósito (tasas con intervalos de confianza de Wilson), no predictivo.
Tecnologías
Python (pandas, openpyxl, matplotlib), Jupyter, Google Forms, Google Sheets y Apps Script, Looker Studio
Estado
Finalizado.
  • Repositorio en GitHub de TSU Academic Tracking
  • Demo interactiva (simulación)

Modelo de cross-sell — Azure MLOps

Estimar qué clientes de un banco tienen más probabilidad de contratar un nuevo paquete de productos.

Modelo de clasificación supervisada construido con metodología KDD y diseñado para llevarse a producción de punta a punta en Azure Machine Learning.

  • Python
  • scikit-learn
  • LightGBM
  • Azure ML
  • MLflow
Ver detalle de Cross-sell Model — Azure MLOps
Problema
Un banco necesita estimar qué clientes tienen más probabilidad de contratar un nuevo paquete de productos, para mejorar la conversión de sus campañas y colas de contacto.
Solución
Un modelo de clasificación supervisada con metodología KDD: una tabla analítica a nivel cliente con variables agregadas en ventanas de 3 y 6 meses, un mes de separación para evitar data leakage, y una comparación de regresión logística, árbol de decisión, Random Forest y LightGBM evaluados con ROC-AUC, KS y lift por decil. Está diseñado para llevarse a producción en Azure Machine Learning: data assets versionados, pipelines con SDK v2 que reutilizan el mismo código de los notebooks, un control de calidad antes de registrar el modelo, endpoints administrados para el scoring y monitoreo de drift.
Tecnologías
Python, scikit-learn y LightGBM, Azure Machine Learning (SDK v2), MLflow
Estado
En curso — las métricas finales (AUC-ROC, KS, lift del primer decil) todavía no están publicadas en el README.

Proyecto final de carrera

StockifAI2 — Gestión de inventario

En los talleres automotores, tener demasiados repuestos inmoviliza plata y genera obsolescencia, y tener pocos deja autos parados esperando una pieza.

Un producto web completo que centraliza el stock de uno o varios talleres, pronostica la demanda semanal de cada repuesto para las próximas 4 semanas y genera alertas automáticas de quiebre inminente, stock bajo y sobrestock.

  • Angular 18
  • Django REST Framework
  • LightGBM
  • MySQL 8
  • Auth0
  • AWS
Ver detalle de StockifAI2
Problema
En talleres y concesionarios, tener demasiados repuestos inmoviliza plata y genera obsolescencia, y tener pocos deja autos parados esperando una pieza.
Solución

Un producto web completo que centraliza el stock de uno o varios talleres, pronostica la demanda semanal de cada repuesto para las próximas 4 semanas y genera alertas automáticas de quiebre inminente, stock bajo y sobrestock.

Incluye un tablero de inventario con KPIs y reportes en Excel, clasificación de rotación de cada repuesto, un mapa para encontrar qué taller del grupo tiene una pieza, un catálogo de repuestos, importación masiva de stock desde Excel, y talleres, grupos y usuarios con roles.

El pipeline de ML segmenta los repuestos en venta frecuente e intermitente, construye variables de rezagos, ventanas móviles, calendario (con feriados argentinos) y macroeconomía, entrena un modelo LightGBM por segmento con validación temporal y pronósticos rodantes, y corre automáticamente cada semana o a pedido desde la API.

Tecnologías
  • Frontend: Angular 18, Bootstrap 5, Chart.js, Leaflet
  • Backend: Django 5, Django REST Framework, django-crontab
  • Machine learning: LightGBM, scikit-learn, pandas, NumPy
  • Base de datos: MySQL 8
  • Autenticación: Auth0 (JWT)
  • Infraestructura: AWS, Nginx, Gunicorn
Estado
Proyecto final de Ingeniería en Sistemas de Información, UTN.
